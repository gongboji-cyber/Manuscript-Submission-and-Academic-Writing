# 工作区、文档结构与阶段门禁

本文件定义软著材料项目的默认工作区。设计参考 Fokkyp/SoftwareCopyright-Skill 的“分析/草稿/正式资料”分层与关键确认门禁，但保留本仓库更严格的事实台账、权属审计、证据链和 GO/HOLD/STOP 体系。

## 1. 默认工作区

在被分析软件项目根目录下建立：

```text
软件著作权申请资料/
├─ 00_状态与索引/
│  ├─ README.md
│  ├─ STATUS.md
│  └─ generation-report.md
├─ 01_项目证据/
│  ├─ 软件事实台账.md
│  ├─ project-inventory.json
│  ├─ 业务理解.md
│  ├─ 业务理解.json
│  └─ 第三方组件台账.csv
├─ 02_草稿/
│  ├─ 申请表信息.md
│  ├─ 代码文件候选清单.md
│  ├─ 代码文件选择.json
│  ├─ 软件说明书.md
│  ├─ 截图计划.md
│  └─ 一致性矩阵.md
├─ 03_截图/
│  ├─ 原始/
│  ├─ 正式/
│  └─ 截图证据.csv
├─ 04_正式资料/
│  ├─ 申请表信息.txt
│  ├─ <软件全称>_软件说明书.docx
│  ├─ <软件全称>_源程序鉴别材料.docx
│  └─ PDF/
├─ 05_内部审计/
│  ├─ 权属事实说明.md
│  ├─ 第三方代码审计.md
│  ├─ 源码分页QA.csv
│  ├─ 最终一致性审计.md
│  ├─ 人工视觉QA.md
│  └─ FINAL_VERDICT.md
└─ 06_开发证据链_可选/
   ├─ provenance/
   ├─ timeline/
   ├─ tests/
   ├─ regression/
   ├─ release/
   └─ hashes/
```

原则：

- “正式资料”只放准备上传/填报的材料，不混入内部审计。
- “内部审计”默认不上传登记系统。
- “开发证据链”是防御性归档，不是普通登记必交材料；不得伪造 Git、日志或历史文档。
- 用户已有成熟目录时不强制搬迁，可建立映射表而不是破坏现有工程。

## 2. 业务理解先于文案

正式写申请表和说明书前，先生成 `业务理解.md/json`。至少回答：

- 软件真实用途、目标用户、输入、处理、输出；
- 软件类型：GUI / Web / CLI / 数据管线 / SDK / 服务 / 插件；
- 核心功能与对应代码/页面证据；
- 运行方式与环境；
- 不存在的功能边界；
- 哪些内容属于第三方依赖而不是本软件功能。

业务理解不是营销稿，也不是算法论文摘要。

## 3. 代码选择必须有候选清单

先生成 `代码文件候选清单.md` 和 `代码文件选择.json`，每个候选至少记录：

- 文件路径；
- 是否第一方；
- 是否生成代码/测试/配置/第三方；
- 与软件功能的关系；
- 是否选入；
- 选择理由；
- 连续性风险。

模型应根据真实软件类型选择最能代表软件主体逻辑的源码。不要机械“前端优先”；CLI/科研软件可以优先入口、核心业务、I/O、指标、报告、可视化等真实模块。

如果总程序不足 60 页，按真实程序规模提交全部，不为凑页数添加代码。

## 4. 文档类型按软件形态选择

### A. GUI / Web / 移动端：操作手册优先

推荐骨架：

1. 相关文档
2. 软件说明
3. 功能特点
4. 系统要求
5. 安装/登录/初始化
6. 按真实页面或用户流程逐章操作
7. 输出、保存、导出
8. 常见问题
9. 术语表
10. 版本信息

每个核心页面应自然说明：用途、入口、可见内容、用户动作、限制/异常、结果反馈、真实截图。

### B. CLI / 科研分析工具：使用说明书优先

推荐骨架：

1. 软件概述
2. 软件总体架构
3. 运行环境
4. 安装与启动
5. 命令与功能模块
6. 典型端到端流程
7. 输入与输出
8. 异常处理
9. 技术特点
10. 软件限制
11. 版本说明

不得为了套 GUI 模板虚构登录页、首页或按钮。

### C. SDK / API / 后端服务：接口/使用说明优先

推荐骨架：

1. 软件概述与边界
2. 部署/运行环境
3. 组件与模块
4. 接口或调用方式
5. 参数与数据结构
6. 返回值/错误码
7. 典型调用流程
8. 安全/权限（真实存在时）
9. 限制
10. 版本说明

## 5. “相关文档”章节的使用

可吸收 SoftwareCopyright-Skill 的“相关文档”做法，但不能虚构总体设计、详细设计、测试案例。

只有项目真实存在这些材料时，才以表格列出：

| 文档 | 状态 | 用途 | 路径/证据 |
| --- | --- | --- | --- |

若没有，不为了模板完整而制造历史同期文档。可以写“本次未附其他配套文档”，或直接省略本章。

## 6. 截图工作区

截图必须来自真实软件运行。

`截图计划.md` 先定义：

| 图号 | 功能 | 真实操作/命令 | 预期画面 | 隐私风险 | 获取方式 |
| --- | --- | --- | --- | --- | --- |

截图后生成 `截图证据.csv`，至少包括：

`figure_id, filename, command_or_action, capture_time, source_output, sha256, redaction, status`

允许裁剪无关边缘和遮挡隐私；不得修改软件输出和结果。

## 7. 阶段门禁

默认门禁：

### Gate 1 — BUSINESS_UNDERSTANDING_CONFIRMED
用户确认软件业务口径，或用户明确授权 agent 一竿到底并允许在无冲突时采用事实证据。

### Gate 2 — APPLICATION_FACTS_CONFIRMED
至少确认：软件全称、版本、著作权人、开发方式、权利取得方式、完成日期、发表状态。

### Gate 3 — CODE_SELECTION_CONFIRMED
确认源码候选、排除项、源程序量与交存策略。

### Gate 4 — SCREENSHOT_PLAN_CONFIRMED
确认真实截图来源；CLI/无 GUI 软件可采用命令行和真实结果图。

### Gate 5 — FINAL_DRAFT_CONFIRMED
确认申请字段、说明书、代码材料、一致性矩阵。

### Gate 6 — MANUAL_RENDER_QA
Word/WPS/PDF 最终人工检查；未完成时状态不得写 READY_FOR_SUBMISSION。

若某已确认事实后来改变，对应门禁自动失效并重新确认。

## 8. 正式材料命名

建议：

- `申请表信息.txt`
- `<软件全称>_软件说明书.docx`
- `<软件全称>_源程序鉴别材料.docx`

如程序超过 60 页且采用普通交存，也可拆分为前 30 页/后 30 页文件；是否拆分以当前系统上传要求为准。

## 9. 正式资料与内部材料严格分离

正式材料禁止残留：

- TODO / TBD / 待确认 / 提交前更新；
- Codex / ChatGPT / agent 内部指令；
- READY_FOR / HOLD / audit / freeze 等内部状态词；
- 私人绝对路径、token、密钥、身份证号（除官网要求的身份材料）；
- 与申请无关的论文投稿、项目代号、审稿记录。

内部审计材料可保留这些信息，但默认不上传。

## 10. 最终输出状态

文档生成完成但未人工渲染：
`READY_FOR_MANUAL_FINAL_QA`

所有 P0/P1 关闭、人工 QA 完成、当前官网字段核验：
`READY_FOR_SUBMISSION`

存在关键事实或权属冲突：
`HOLD` 或 `STOP`
