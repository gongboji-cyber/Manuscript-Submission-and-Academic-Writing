# 权属、合作开发与第三方代码风险

## 1. 为什么必须单独审

软著登记材料做得漂亮，不代表申请人一定拥有权利。权属错误比排版错误严重得多。

## 2. 独立开发

只有在事实支持时才能写“独立开发”。

核对：

- 代码主要由谁完成；
- 是否使用单位资金、设备、未公开信息；
- 是否属于本职工作或明确开发任务；
- 是否存在雇佣/实习/合作关系。

## 3. 职务开发

自然人在法人或组织任职期间开发的软件，在符合《计算机软件保护条例》相关条件时，著作权可能归法人或组织。

因此学生、员工、实习生项目不能仅凭 GitHub 账号就判断权属。

## 4. 合作开发

两人以上共同开发时，优先查书面协议。

必须确认：

- 谁是著作权人；
- 是否共同享有；
- 是否存在可分割部分；
- 申请人是否有权以当前方式申请。

## 5. 委托开发

委托人与受托人之间应看合同约定。没有合同或约定不清时不能凭常识填“委托方所有”。

## 6. 基于原软件修改

如果是在他人原软件基础上修改，并以修改后软件申请登记，应检查原著作权人的许可及修改是否形成符合要求的软件。

## 7. 第三方依赖

第三方依赖本身并不当然阻止登记，但不能把第三方源代码作为申请人原创主体材料。

分类：

- 仅作为依赖调用：通常排除其源码；
- vendored 进项目：识别许可证与来源；
- 复制后修改：高风险，需证明授权和修改关系；
- 生成代码：标记生成器和来源；
- 模板/脚手架：区分模板部分与项目新增部分。

## 8. 开源许可证

至少扫描：

- MIT / BSD / Apache-2.0；
- GPL / LGPL / AGPL；
- MPL；
- 专有或非商业许可证；
- 无许可证来源。

本 skill 不自动给出复杂许可证兼容性的法律结论，但应把高风险组件列入待确认表。

## 9. 代码来源异常

出现以下情况默认 HOLD 或 STOP：

- 大量文件 copyright 属于其他主体；
- 关键模块来自公开仓库且几乎未修改；
- README 与申请人描述明显不符；
- 提交历史显示软件主体由其他人完成；
- 代码中保留他人公司/产品名称；
- 用户要求删除来源信息后冒充原创。

## 10. 证据台账

权属相关事实建议保存：

| 事项 | 证据 | 结论 | 风险 |
| --- | --- | --- | --- |
| 独立/合作/委托/职务 | 合同/任务书/陈述 |  |  |
| 申请人 | 身份/主体材料 |  |  |
| 第三方依赖 | lockfile/LICENSE |  |  |
| 原软件许可 | 许可文件 |  |  |
| 代码作者 | git history |  |  |

没有证据时写“不确定”，不要生成确定结论。
